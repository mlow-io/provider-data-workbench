# Reviewed-field materialization contract S1.3

Selected for implementation 2026-11-21. This first bounded slice materializes one explicitly selected, current office phone decision into a candidate derived from the current approved feed version. It does not edit source bytes or claim provider verification. Address and bulk edits are outside this slice.

A request pins base version, clinician and reviewed location identities, field-view snapshot, latest selected decision ID, actor, reason and an idempotency key. The base must remain current and approved. Both identity links and the selected decision must be fresh; exactly one non-quarantined base row must be linked through its retained receipt, attempt and row locator to the reviewed scope. Reject unresolved/conflicting/stale decisions, ambiguous or absent row links, wrong scopes, invalid phone values and changes that leave normalized phone and extension unchanged. No matching by NPI alone. Source preference must be selectable and its phone and extension remain one assertion.

Candidate creation is transactional and retry-safe by request key, including after restart or approval. It preserves every original row and copies the complete roster, changing only that row's normalized phone and extension. Candidate manifest and row lineage pin base, reviewed scope, link/evidence snapshot, decision, selected source and original/proposed values. The selected source artifact's digest is checked at creation and again at approval. Reusing a key with different inputs fails; a different key cannot create a second candidate for the same base, scope and decision. Candidate creation never approves a dataset. The original approved version remains consumable.

A separate explicit dataset decision rechecks the base/current version and all pinned source/link/field snapshots and rejects stale candidates; it retains the source approval's quality holds and acknowledgments. The inherited quality report describes the base, including its comparison findings; it is not a newly calculated comparison of the correction. Only approval advances the feed pointer. Derived jobs are labeled and cannot be reprocessed as source deliveries; a new candidate requires a current reviewed scope. Export includes the derived normalized value and traceable lineage; old pinned exports and original artifacts remain unchanged. A locally approved correction is not independent verification or payer writeback. Restart and identical retries reproduce the same candidate and approval results.

The discovery endpoint pages latest selected phone scopes in the database before inspecting their evidence. Its `total` counts reviewed scopes, not eligible corrections; a page may contain no choices while `next_offset` is present. Callers follow `next_offset` to continue. The POST endpoint requires the exact returned scope, snapshot and decision, together with attribution and a request key. Concurrent creation is serialized with the approval and identity checks in a database transaction.

Acceptance: two offices with one clinician; select NORTH's phone, retain SOUTH unchanged, create candidate without promotion, approve separately, inspect approved JSON and workbook including lineage, and reopen. Exercise stale base/link/decision, unlinked and ambiguous rows, conflict, wrong scope, no-op, repeat/restart and conflicting request key. Tests use isolated synthetic storage.

## Subsequent source delivery

A later file keeps its source-to-source comparison against retained observations. Separately, `report.effective_corrections` compares incoming phone/extension assertions to previously corrected rows in the pinned approved version using exact native record/office keys. Changed, missing, invalid or ambiguous incoming assertions raise the `effective_correction_drift` soft hold. An operator must acknowledge the risk before approving the new source version; a source repeating the old phone cannot silently appear safe merely because its source comparison is unchanged. Missing still does not mean termination. No old observation or local decision is rewritten, and approval of a later source does not claim a payer update. Bounded UI samples keep full totals; the complete approved-dataset JSON retains the whole report.

## Complete pre-approval review evidence

The interactive version detail remains a bounded sample. Any candidate, approved or rejected version may download its complete immutable quality report through `GET /api/feed-versions/{id}/quality-report`. The attachment identifies the version, feed, current decision state and pinned report hash and explicitly states that it is review evidence, not an approved dataset export. It includes the entire source comparison, effective-correction comparison and quality findings, without producing an approved-dataset records envelope or changing any state. Comparison entries may contain normalized provider values needed for review; this is an approval boundary, not a confidentiality control. Approval and consumer-export gates remain unchanged. An operator must be able to inspect a correction drift outside the first 50 displayed entries before acknowledging its hold.

The corrected-roster comparison can also be filtered by status and paged in the version detail. Each page requires the selected report hash; stale hashes fail instead of displaying another report. Counts above the filtered view still describe all assessed keys. The complete quality-report attachment remains available.
