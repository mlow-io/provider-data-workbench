## NPPES Registry v2.1

[Official API help](https://npiregistry.cms.hhs.gov/registry/help-api). Supports exact NPI and bounded city/state searches, default 25, maximum 200, with explicit skip. One request produces one bounded intake; there is no automatic national harvest. Preserve `number`, entity type, full `basic`, addresses, additional practice locations, taxonomies and other original fields. Unknown status stays unknown. All locations remain together at native entity grain; no mailing address is silently treated as a confirmed practice.

`basic.last_updated` is `source_updated_at`, never human verification. The legacy CSV sample helper is still available, selects one address/taxonomy for its projection, uses native NPI IDs, and now leaves human verification blank.

## CMS Doctors and Clinicians

[Dataset mj5m-pzi6](https://data.cms.gov/provider-data/dataset/mj5m-pzi6), [dictionary](https://data.cms.gov/provider-data/sites/default/files/data_dictionaries/physician/DOC_Data_Dictionary.pdf), [API information](https://data.cms.gov/provider-data/about). Fetch dataset metadata before a small datastore distribution-0 page; retain the metadata with the original response receipt. API supports a bounded limit/offset. It does not expose arbitrary query expressions or promise filtered national coverage.

Native grain is clinician/enrollment/group/address. Retain all rows, including incomplete composite keys as unresolved; never deduplicate on NPI. Published labels and observed lowercase/underscore machine columns have contract tests. CMS coverage concerns Medicare, not all clinicians or commercial payer networks. Dataset publication/modification dates do not establish per-provider verification.

## Retrieval behavior

Only connector-owned HTTPS hosts are fetched. Redirects outside the source host are rejected. Responses cap at 10 MiB and pages at 200 rows. Transient HTTP/network failures have at most three attempts, with bounded `Retry-After` handling. Error envelopes, malformed success responses and connection failures remain visible failures, not healthy empty directories. Response bytes are retained when available; a capped failure prefix is labeled truncated. Connection failures have no invented response artifact.

A fifteen-minute retained-response cache creates a new receipt with `cache_status=retained_response`; `refresh=true` requests a fresh read. Saved `flat`, `nppes`, and `cms` JSON profiles use the same ingestion service and produce normal previews/quarantine/acceptance. Unsupported envelopes are rejected visibly. Zero results are a successful bounded retrieval with zero accepted rows.

## D2.0 selected acquisition contract

Selected and implemented in D2.1 on 2026-11-14 with Sources-workspace controls. Use one source key `hap` with the fixed production HTTPS origin published above. Operator input selects Location or PractitionerRole and a count of 1–20; role search includes only practitioner/location/organization/network references. No arbitrary URL or clinical-resource path is accepted. Source-advertised Plan-Net 1.0.0 and parser-target subset 1.2.0 remain distinct metadata.

Schema 12 adds `fhir_acquisition` (request identity/configuration, revision, state, checkpoint, result receipt) and append-only `fhir_acquisition_event` (request/response/error/transition evidence with optional artifact hash). Back up populated schema 11 before migration. Reuse the existing artifact store and one nonblocking local worker lock. No daemon or scheduler is installed. Each explicit worker pass performs at most one request; long rate-limit waits persist `next_retry` and return immediately.

Cooldown applies to the configured source base across acquisitions within one workbench, including completed/cancelled operations. Immutable request/response events retain `source_wait_until`; a longer Retry-After remains effective if its originating intent is cancelled. Existing non-null retry checkpoints are also honored. A waiting new operation records a `source_wait` event without consuming request budget or fetching. Registry metadata exposes `source.next_request_at`; local final publication is exempt because it performs no source request. This closes the per-operation cooldown gap found by the D4 completion audit without changing the durable schema.

Bounds: three search pages, twelve direct supported-reference reads, twenty-four total HTTP requests, 200 assembled entries, 2 MiB per response and 10 MiB retained response bytes, ten-second socket timeout and ninety seconds cumulative active fetch time. Default source spacing is thirty seconds. At most three attempts per transient URL failure; retain each response and honor larger Retry-After rather than sleeping. Redirects are retained, then validated before a later pass. Permit only the configured HTTPS origin, four supported provider-resource paths and bounded paging query keys; reject userinfo, fragments, encoded paths and cross-host destinations. Test-only loopback HTTP source configuration is injected through the service constructor, never through an HTTP payload.

The post-D4 live capture returned a valid searchset whose next link advertises `https://fhir-prov-dir-r4.api.hap.org:443` and `_pretty=true`. The follow-up implements this source-specific routing rule: recognize only that exact HAP hostname (with absent or explicit default 443), plus the published hostname's explicit default 443, and route its path/query back through the fixed published HTTPS origin. No request goes to the advertised alias. Unknown hosts, nondefault ports, userinfo, fragments, encoded paths and unsupported resource/query paths remain rejected. Permit `_pretty` only as one `true`/`false` formatting value, within unchanged response/page/time bounds. No HTTP payload can configure aliases. Test-only sources do not inherit this production rule.

Retain the original alias URL as `source_url` on routed pending requests and response bodies/events, alongside the actual published-origin request URL. Raw responses are unchanged. For a directly retrieved reference, the derived entry's `fullUrl` uses this advertised URI when present so original references resolve without rewriting resource values; resource-origin provenance still names the actual HTTP request URL. Redirects retain original response/Location evidence. This is additive checkpoint/event metadata with no schema migration, automatic identity link or expanded network destination. The failed pre-fix capture remains failed; a new explicit intent must demonstrate the corrected route.

Resolve a relative supported reference in its originating resource's declared REST base when `fullUrl` ends in its resource type/id, matching the pure parser. Absent/URN bases use the configured source; an explicitly out-of-scope REST base is rejected rather than silently fetched from the configured source. Routed reference identity remains its advertised URI, while request provenance names the gateway.

The same bounded follow-up adds optional `resource_id`, a source-native Location/PractitionerRole ID matching `[A-Za-z0-9.\-]{1,64}`. Reject null, blank, nontext or path/query fragments. Emit one `_id` search parameter under the selected resource, alongside existing count/includes. Persist the exact filter in immutable acquisition configuration and filtered receipt query/scope metadata; old unfiltered scope hashes remain unchanged. Page size limits a response, not total results. A native ID filter makes one specific source query possible without adding arbitrary query input or treating NPI as an office ID. Existing destination/request/page/byte/retry/cancellation and separate acceptance rules still apply.

Each raw page/reference/error body is an exact separate artifact, with selected response headers and retrieval/request information. A derived searchset is assembled only after bounded traversal finishes. Identical entries can share an assembled resource while retaining every original page/entry origin; conflicting versions remain distinct. The derived artifact and receipt are explicitly labeled assembled evidence. Per-resource origins connect assembled JSON locators to exact raw response artifact hashes/entry paths. Field provenance carries those origins. Completing a bounded query is not full-directory coverage.

States are queued, running, retry_wait, failed, cancelled and complete; checkpoint data records pending/fetched URLs, successful bodies, page/reference counts, byte/time/request/retry budgets and next retry. Partial state is explicit when successful bodies precede failure. Revision checks fence concurrent cancellation. The OS lock serializes workers; after process death a later worker resumes the durable checkpoint. A crash before committing a response can repeat a read, but cannot duplicate accepted observations. Final receipt/attempt/result publication is one SQLite transaction with deterministic identity. Complete acquisitions still require normal separate reference-resource acceptance; partial/failed/cancelled acquisitions cannot publish a ready receipt or promote a clinic dataset.

Implemented list/detail/create/run-once/cancel APIs plus exact response-artifact download. Configure source/query through allowlisted fields and receipt-scoped actor/reason/request identity. Preserve request-ID identical-intent recovery and reject changed intent. Controlled HTTP tests must cover multi-page/reference assembly and original-byte lineage, redirects, 429/due retries, unsafe URLs, later-page/malformed failures, budgets, cancellation, crash/restart, duplicate execution and preservation of a prior approved clinic export. Later live qualification completed one native-ID-filtered Location capture and explicit local reference acceptance, plus two routed actual search pages deliberately cancelled before publication. [The live-boundary receipt](evidence/canonical/fhir-live-boundary-2026-11-14/README.md) records exact hashes and limits. Live PractitionerRole/network graph and target-profile conformance remain unverified; this result applies only to the observed Location and transport steps.

## D2.1 operational web integration contract

The Sources workspace owns bounded FHIR captures. Loading or refreshing it performs local reads only. Show the server-configured origin, source-advertised/parser-target versions, limits, retained captures and their states. Creation requires an operator, reason, resource type and count, preserves an unchanged request ID after an uncertain response, and queues work without fetching. Each explicit **Run one capture step** action performs at most one request or final publication. No background polling, retry timer or scheduler starts network requests. Show the persisted due time and allow refresh/cancellation while waiting.

Select captures through a durable workspace query. Detail shows scope, completed pages/references, requests/bytes, partial/error state, due time and append-only history with exact original response downloads. Cancellation requires current revision, operator and reason; stale errors preserve the draft and offer refresh. A complete result links to its separate intake review; no capture action accepts evidence or changes an approved clinic dataset. Distinguish original response downloads from the derived searchset. Controlled browser journeys use an invocation-owned loopback HTTP source injected only in the browser test launcher; production still accepts only its fixed source.

## Filtered-response integrity (R1)

Frozen before R1 implementation. [FHIR R4 search](https://hl7.org/fhir/R4/search.html#id) defines exact case-sensitive `_id` matches, and [Bundle search modes](https://hl7.org/fhir/R4/bundle-definitions.html#Bundle.entry.search.mode) distinguish `match`, `include` and `outcome`. The following is this workbench's conservative filtered-evidence policy, not a complete server conformance test.

For an acquisition configured with `resource_id`, each page is structurally parsed and its search entries checked before it advances. Explicit `match`, or an omitted mode, requires the configured resource type and exact ID. Omitting mode never silently classifies another resource as an include. A malformed search object, unknown/null mode, missing resource or mismatching identity fails the capture with retained response/error evidence and no ready receipt. Explicit `include` entries preserve supported/unsupported resources with their own native eligibility rules; their IDs need not equal the requested root. An `outcome` entry must contain a nonempty, well-formed OperationOutcome issue list with known severities and nonblank text issue codes. This does not certify issue-code terminology. Warning/information outcomes remain context; error/fatal or malformed outcomes fail even under HTTP 200. Resource validity and query integrity remain separate judgments.

At final publication revalidate all retained search pages against the immutable configuration and verified artifact hashes. This covers queued captures made before R1 and restart without another source request or trusting new checkpoint counters. Include-only results cannot publish without at least one matching entry across the completed page set. A genuinely empty search, or warning-only outcome with no includes/matches, can complete as empty reference scope; it does not prove termination. Direct reference reads retain their existing requested type/id check and are excluded from search-entry counts. Previously completed receipts/decisions are never reinterpreted in place.

New filtered receipts add `metadata.query_validation` with `version=1`, requested `resource_type`/`resource_id`, `matched_entries`, `implicit_match_entries`, `included_entries`, `outcome_entries`, and `scope=captured_search_pages`. `implicit_match_entries` is a subset of matches. Counts refer to exact retained page entries, including duplicates, rather than deduplicated assembled entries or Bundle.total. When an identical resource is both included and matched across filtered pages, the derived entry gives the matching entry precedence while preserving every raw page/origin and original search metadata. This report also appears in the publication event. It proves the local rule was applied to the captured payload, not source truth, profile/terminology conformance, complete-directory coverage or approved clinic data. Unfiltered metadata and old completed filtered receipts remain unchanged. Native review exposes the report or explicitly states that an older filtered capture lacks it. Failed/partial data has no intake-acceptance path.

## Strict retained JSON consistency (R4)

Frozen before implementation. Saved/search Bundles and standalone supported reference responses must share strict UTF-8 JSON decoding before any identity check, projection or assembly: reject duplicate object properties at every depth, NaN/Infinity and overflow-to-nonfinite numbers, depth greater than 64, more than 100,000 nodes, and the existing 10 MiB parser bound (transport retains its smaller response bound). UTF-8 BOM remains accepted. Keep Bundle envelope/entry checks in the native parser; the shared decoder does not infer profiles or accept resources.

Digest-verified retained responses must use the same decoder on publication/restart so pre-fix queued captures cannot hide ambiguous original reference bytes behind a previously normalized object. A failed response stays downloadable with its exact hash/HTTP status; it creates no receipt/observations or approved-version change. Old completed receipts and immutable attempts remain unchanged. This fixes acquisition consistency without changing the v2 parser's supported output/schema or adding another source family.
